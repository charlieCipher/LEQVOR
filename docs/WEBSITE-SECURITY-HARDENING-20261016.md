## Existing controls inspected and preserved

- Authentication: 16-character new-password policy; existing-password compatibility; enumeration-resistant reset/resend UI; exact-account reauthentication and fail-closed MFA assurance checks. Passkeys remain restricted to the established production relying-party origin. No live biometric ceremony was performed.
- Session/key separation: Supabase manages account tokens; vault key remains in `VaultSession`, with lock on blur/background/timeout, generation checks for asynchronous disclosure and object URL cleanup. Account password reset does not supply the vault key. Browser refresh-token storage remains the SDK's existing local persistence; a successful same-origin script compromise would remain serious.
- Data/authorization: owner/vault composite identity constraints, restrictive owner RLS, optimistic revisions, atomic record/file/graph saves, owner-only encrypted history. Existing disposable SQL matrix covers guessed UUIDs, cross-account reads/writes, stale updates and transactional rollback. No additional cross-account bypass was established in those tests.
- Sharing/family/beneficiaries: graph/role relationships do not themselves grant ciphertext access. Explicit accepted, unexpired record-revision shares and individually selected file wrappers are required; owner-only table/storage policies are retained. Download proxy authenticates first and rechecks revocation after retrieval. Revocation cannot erase plaintext a recipient previously downloaded.
- Encryption/files: authenticated AES-GCM with fresh random nonces and purpose/identity AAD, fixed bounded Argon2id parameters, independent document keys, verified recipient-key fingerprints and separate recovery derivation. File storage is private JSON ciphertext; downloads use application/octet-stream rather than executing uploaded HTML. No crypto algorithm replacement or migration of customer ciphertext was attempted.
- Rendering/routing: active React paths render user text through React; fixed internal routes and encoded identifiers. Legacy RecoveryPhrase's generated-word printing path was not reported as an attacker-controlled XSS. No reachable confirmed XSS or SQL injection was found during this source review.
- Supply chain: pinned dependencies and checkout/setup actions, read-only CI permissions and no production secrets in the website test job. Dependency audit returned zero reported vulnerabilities; that is not proof packages are defect-free.

The public HTML cache policy is public/max-age=0/must-revalidate; private API responses remain no-store. No Set-Cookie on the public document is not a claim about SDK token persistence.

Supabase URL Configuration: Site URL `https://leqvor.vercel.app`; exactly two redirects, `https://leqvor.vercel.app` and the previously authorized `http://127.0.0.1:5173`; no wildcard seen. Remove the production loopback callback only as a reviewed rollout change after local development uses its separate backend.

Supabase Rate Limits: sign-in/sign-up 30 requests/5 minutes/IP; token verification 30/5 minutes/IP; refresh 150/5 minutes/IP. Custom SMTP per-user minimum interval displays 1 second. Email-send aggregate limit was redacted by the browser tool and was not recovered. Consider an approved increase of the per-user email interval to 60 seconds; the UI cooldown alone is not server enforcement. No test emails were sent during this review.

Supabase Sessions: access JWT expiry 3600 seconds; refresh-token replay detection enabled with 10-second reuse interval. Single-session, session lifetime and inactivity settings are unavailable on the displayed Free plan; no paid upgrade was initiated. Immediate invalidation of every previously issued access JWT is not established by these settings or a client-side sign-out.

Vercel: service-role key, backend server URL, cleanup flag and cron secret are Production-only; their secret values were not revealed. System Environment Variable exposure is currently unchecked. The proposed code requires authoritative environment metadata: confirm actual build/runtime `VERCEL_ENV` availability or approve enabling system-variable exposure before rollout. Missing metadata must block deployment, not silently assume production.

Hosted catalog-only queries also confirmed RLS enabled and forced on records/vaults, with direct authenticated record deletion revoked; private vault-v5 bucket has 16,000,000-byte limit and application/json MIME allowlist. Legacy assets/profiles have RLS enabled but not forced, and assets' displayed policies are owner user_id checks. Legacy vault bucket is private but has no explicit per-bucket size/MIME restriction (global project limits were not inspected). This is recorded as a legacy constraint gap, not claimed as cross-account access or executable-file XSS. The prepared MFA guard covers legacy user_id ownership and profiles as well; current V5 file constraints remain unchanged.

## Staging and rollout requirements

1. Review this branch separately from branding and Founder Authority. Do not treat PR #2's approval as approval for these security changes.
2. Provide/approve a separate empty staging Supabase project; never copy customer rows, ciphertext, auth users or keys. Apply reviewed customer migrations there through a separately approved process. Use a private vault-v5 bucket with the same size/MIME/RLS contracts. Use only synthetic identities/files.
3. Restrict production public variables to Production and put staging public/server variables only in Preview. Staging server keys must belong to the staging project. Cron stays disabled in staging unless explicitly approved; never copy CRON_SECRET or server keys from production.
4. Exact required deployment variables: authoritative `VERCEL_ENV`/`VERCEL_TARGET_ENV`; existing `VITE_SUPABASE_URL`, public `VITE_SUPABASE_ANON_KEY` or `VITE_SUPABASE_PUBLISHABLE_KEY`; for staging only, server/build-only `LEQVOR_STAGING_SUPABASE_URL` and `LEQVOR_STAGING_ORIGINS` (JSON array of exact HTTPS app origins). APIs additionally need their environment's `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. No server secret may have a VITE_ prefix. Passkey pilot flag remains false for staging.
5. Configure staging's Supabase Site URL/redirect list to its exact staging origin(s), separate from production. Review an actual staging Vercel configuration with connect-src pinned only to that staging project. The build checks `vercel.json` (or the explicit `LEQVOR_VERCEL_CONFIG` path) against the selected backend; an override path is a local config check, not an assertion that Vercel loaded that file. Vercel must use the SAME reviewed config at deployment. The current committed production CSP deliberately blocks a staging build until that configuration is supplied. No wildcard Supabase CSP was introduced.
6. Run `supabase/tests/customer_security_readiness.sql` read-only against the hosted project to establish actual schema/policy parity. Then obtain approval for the exact MFA migration, first staging then production, and rerun owner/recipient/MFA acceptance. Do not weaken guards or use an admin user to represent a customer test.
7. Establish approved distributed API abuse controls (Vercel firewall/rate limits or a suitable shared limiter), limits and alerting. A per-instance memory counter would not prove global serverless rate limiting; none is presented as such. Request-size checks occur after Vercel JSON parsing and do not replace the platform's pre-parse size limit.
8. Obtain independent security review and passing checks, merge through protected main, then verify deployed headers, origin isolation, real signup/reset/MFA, owner and recipient file workflows, revocation and recovery. Existing preview deployments need retirement/redeployment or explicit provider-level isolation; this branch cannot modify their immutable bundles.

Until these steps are done, this is a tested preparation, **not complete hosted security sign-off**. No production migration, credential rotation, paid resource, Founder activation or security-hardening deployment occurred in this task.
